# FlutterNetworkLens

> A local, in-app network inspector for Flutter test and release builds.

## 1. Project Overview

**FlutterNetworkLens** is a Flutter developer/testing utility that allows developers and testers to inspect network API activity directly inside a Flutter application.

The primary problem being solved:

> When a Flutter release/test build is shared with a tester or backend developer, they should be able to inspect API requests and responses without connecting the device to a development machine or asking the Flutter developer to check console logs.

The initial version focuses only on this local testing workflow: capture what the app sends and receives, then make it easy for a tester to inspect and share the useful details.

### Primary workflow

```text
Flutter Application
        ↓
FlutterNetworkLens Network Interceptor
        ↓
Capture API Request/Response
        ↓
Store locally
        ↓
FlutterNetworkLens Inspector
        ↓
Tester can inspect
        ↓
Request / Response / Headers / Body / Timing
        ↓
Share Debug Information
```

---

# 2. Initial Goal

Build a **reusable Flutter package/library** that can be integrated into another Flutter application.

The first version should provide:

- Request/response interception for supported Flutter HTTP clients
- Local request history
- Network request list
- Request details
- Response details
- Headers inspection
- Request/response body inspection
- HTTP status
- Request duration
- Search/filter
- Clear history
- Copy useful information
- Share API information

The initial version should work **without any external backend**.

All captured information should remain local to the device.

---

# 3. Scope Boundaries

FlutterNetworkLens is intentionally a local debugging utility, not a debugging platform. It has no backend, cloud sync, accounts, web dashboard, remote debugging, team features, or unrelated observability/product infrastructure.

The current objective is to make the **local network-inspection and tester workflow excellent first**. Do not add product/platform features unless they directly improve that workflow.

---

# 4. Target Users

### Flutter Developer

Uses FlutterNetworkLens while developing or testing an application.

### QA / Tester

Receives a test/release build and needs to determine what API request was made and what response was received.

### Backend Developer

Needs to inspect the exact API request/response generated by the mobile application.

# 6. Initial Technical Stack

Use Flutter/Dart.

Recommended initial dependencies:

- Flutter
- Dart
- Local persistence solution suitable for a developer tool
- Flutter's built-in sharing/platform capabilities where possible

Do not introduce unnecessary dependencies.

FlutterNetworkLens must not be limited to Dio. It should support the HTTP clients used by Flutter applications through small, separate integrations/adapters. Dio is a valuable first integration, but the core transaction model, storage, masking, and inspector UI must remain HTTP-client agnostic so other clients can be supported without redesigning the package.

```text

      ↓

      ↓

      ↓
Response received
      ↓
Capture response information
      ↓
Calculate duration
      ↓

      ↓
```

If the request fails:

```text

      ↓

      ↓
Error
      ↓
Capture error information
      ↓

      ↓

      ↓

```

Failed requests must not disappear from the history.

# 10. FlutterNetworkLens Initialization

The consuming application should have a simple integration API.

Example:

```dart
await FlutterNetworkLens.initialize(
  enabled: true,
);
```

For Dio:

```dart
final dio = Dio();

dio.interceptors.add(FlutterNetworkLensDioInterceptor());
```

For `package:http`:

```dart
final client = FlutterNetworkLensHttpClient();
final response = await client.get(Uri.parse('https://api.example.com/profile'));
```

Other supported clients should have equally small integration APIs. The exact API can be improved during implementation, but a developer should not need to rewrite their networking layer.

# 18. Sensitive Data Protection

This is mandatory even in V1.

Network inspection can contain sensitive information.

The system should support masking sensitive headers and fields.

At minimum, consider:

```text
Authorization
Cookie
Set-Cookie
access_token
refresh_token
password
```

Example:

```text
Authorization: ********
password: ********
access_token: ********
```

Do not accidentally expose credentials through the inspector or sharing feature.

FlutterNetworkLens masks values before they are kept in memory or written to local
storage. This protection therefore also applies to the inspector and future
copy/share utilities. The defaults cover the header names `Authorization`,
`Cookie`, `Set-Cookie`, and `Proxy-Authorization`, along with the body fields
`access_token`, `refresh_token`, and `password` (case-insensitive).

Add application-specific sensitive names during initialization:

```dart
await FlutterNetworkLens.initialize(
  sensitiveHeaderNames: {'X-API-Key'},
  sensitiveBodyFieldNames: {'pin', 'sessionSecret'},
);
```

# 22. Request Retention

Do not allow unlimited network history.

Implement a configurable maximum number of stored transactions.

Example:

```dart
await FlutterNetworkLens.initialize(
  maxTransactions: 200,
);
```

When the limit is reached:

```text
oldest transaction
        ↓
removed
        ↓
new transaction stored
```

This prevents excessive storage usage.

# 30. Error Handling

FlutterNetworkLens itself must not break the consuming application.

If:

```text
storage fails
JSON parsing fails
sharing fails
inspector fails
```

the original API request must continue working normally.

FlutterNetworkLens should behave as an observational/debugging layer.

The application's networking behavior must have priority.

---

# 31. Performance Requirements

The interceptor should have minimal impact on the application.

Avoid:

- Blocking the UI thread unnecessarily
- Excessive synchronous disk operations
- Keeping huge response bodies indefinitely
- Memory leaks
- Unbounded lists

Large responses should be handled carefully.

If practical, configurable body-size limits can be introduced.

# 35. Definition of Done

V1 is complete when a developer can:

1. Add FlutterNetworkLens to a Flutter application.
2. Connect it to a supported HTTP client.
3. Build a test/release APK.
4. Give the APK to a tester.
5. Tester opens FlutterNetworkLens.
6. Tester sees API requests.
7. Tester opens a request.
8. Tester can inspect:
   - URL
   - Method
   - Headers
   - Query parameters
   - Request body
   - Status
   - Response headers
   - Response body
   - Duration

9. Tester can search/filter requests.
10. Tester can copy/share a debug report.
11. Sensitive information is masked.
12. FlutterNetworkLens does not interfere with the application's API behavior.

If these requirements work reliably, **V1 is successful**.

# 36. Development Rule for Codex

When implementing this project:

### Follow these principles

- Do not over-engineer.
- Do not implement product/platform features outside the local inspection workflow.
- Do not introduce dependencies without a reason.
- Prefer simple, maintainable Flutter architecture.
- Keep package APIs clean and minimal.
- Write production-quality Dart.
- Use null safety.
- Handle errors properly.
- Keep UI and business logic separated.
- Document public APIs.

### Most important rule

**Solve the tester's network-inspection problem first.**

Do not expand the scope until the local inspector workflow is stable.

---

# Final Product Principle

FlutterNetworkLens should answer one simple question:

> "What exactly happened between my Flutter application and the backend?"

The tester should be able to answer that question **directly from the application without opening a development machine or asking the Flutter developer to inspect console logs.**
